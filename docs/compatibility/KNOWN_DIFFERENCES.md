# Known differences and evidence gaps

## ASCII numeric text policy — 2026-11-08

Per the user's revised scope, signed integer text is parsed with Rust standard
`str::parse::<i32/i64>()`. Only ASCII decimal digits are supported. Leading `+`/`-`,
signed minima/maxima and overflow checks remain; whitespace, fullwidth digits,
Arabic-Indic digits and other non-ASCII digits are rejected. This intentionally
differs from Java `Integer.parseInt` / `Long.parseLong`.

This applies to message numeric properties and flags, permissions, remoting
ports/settings, route queue counts/VIP ports, header numeric text, TopicConfig text,
Consumer timing properties and consume timestamp fields. Existing callers retain
their error or fallback behavior for invalid numeric input (for example priority
uses its existing default); failed expired-message timestamp parsing retains the
message instead of sending it back. Timestamp calendar normalization remains lenient.

Java fixtures continue to describe Java behavior. Rust tests compare supported ASCII
cases and explicitly assert rejection/fallback for out-of-scope Unicode numbers.
Historical Unicode parity records below and in dated inventories are superseded for
this scope. Ordinary Unicode topics, message text and host names are unaffected.
JSON scalar/coercion rules, arbitrary decimal truncation and integer wrapping remain
specialized; substituting ordinary integer parsing would change more than this policy.

## P18 `MessageQueueAssignment` collection-hash boundary

- Java `MessageQueueAssignment.equals` compares only `messageQueue`, while
  `hashCode` also includes mode and attachments. The Protocol JSON decoder now
  matches stable Java `HashSet` bucket behavior when equal queues use the same
  mode and their attachment maps have colliding Java hashes; it also preserves
  Java's null-queue failure when a second equal-hash row invokes `equals`.
  `MessageQueueAssignment` keeps lawful all-fields Rust `Eq`/`Hash` for native
  collections. A different-mode equal-hash collision still depends on the JVM's
  process-local enum identity hashes, so a manually supplied raw array engineered
  for one JVM has no guaranteed cross-process result. A Java Set serialized
  after insertion already reflects that JVM's membership result. See the
  assignment input and method rows in `PHASE_6_API_CONFIG_MAP.md` and fixture
  `fixtures/runtime/lookup.json`.

## P18 compact inner-message counter malformed sizes

- `countInnerMsgNum(ByteBuffer)` moves the Java cursor by each declared size without validating progress. Rust `count_inner_messages` uses a mutable `Cursor` and matches ordinary records, positioned cursors, truncated size prefixes, incomplete positive sizes, finite positive sizes below four, and finite negative sizes. The invoked fixture follows a rewind from offset 8 to 5 before both implementations fail at cursor position 9. For a zero size and an in-range negative-size cycle, both implementations continue looping; child-process probes verify that both remain active after the bounded observation interval. If a negative size would put Java's buffer position outside `[0, limit]`, both implementations fail after consuming the four-byte size prefix. The malformed-loop behavior matches Java 5.5.1 rather than returning a Rust-only guard error.

## Phase 2 Remoting codec

- Java's private serializer writes both absent and empty remark as a zero-length string; Rust preserves the distinction in its command model but the wire decoder returns `None` for either representation. An absent versus empty body similarly collapses to no body when the frame body length is zero.

- Java harness fixtures are offline protocol-command evidence, not live NameServer/Broker outcomes.
- Java-compatible Rust TLS property sources share a process-wide retained property state, matching Java `TlsSystemConfig`; the first explicit system-property map initializes it once, even when TLS mode is Plain, and later maps do not replace those static values. `TransportMode` reads `tls.enable` and the default config path from that initial map; TLS files cannot change them, matching Java's file extractor. Every new `RemotingClient` reloads its retained file source before building the TLS connector, while existing clients keep their constructed context. Omitted file properties retain the latest process value across distinct `TlsConfig` sources. Rust still receives system properties explicitly instead of reading JVM properties implicitly. The invoked Java and Rust regressions are recorded in `PHASE_3_REMOTING_INVENTORY.md` and `docs/release-checklist.md`.
- User decision: Rust is not required to extend TLS key support beyond encryption algorithms and key sizes available from the selected RustCrypto/rustls dependencies. This is limited to provider/library capability gaps, not a waiver for supported Java formats or TLS trust, hostname, mode, and Phase 19 validation behavior.
- Encrypted client PKCS#8 PEM keys are decrypted in pure Rust when `tls.client.keyPassword` is set. Supported formats include PBES1 `pbeWithMD5AndDES-CBC` (including RocketMQ Java 5.5.1's encrypted `client.key`) and PKCS#8 PBES2 schemes supported by RustCrypto (AES-CBC with PBKDF2/SHA-1 or SHA-2, scrypt, and 3DES; DES/3DES support is enabled only for compatibility). A Java 5.5.1 PBES2 + 3DES key/certificate fixture is decrypted and accepted by rustls in `java_pbes2_3des_encrypted_private_key_is_decrypted_and_loaded`; fixture SHA-256: key `401de60297e7d4edb02a585987becc3dede70fcf2e34774678473f7e81517b17`, certificate `436543da7b4d337106dd3695a2a8ddcd4c78d2a0f1e21b1a7856931af6b460c5`. Java fixture source: reference checkout `remoting/src/test/resources/certs/privkey.pem` and its matching certificate. PBES1 MD2/RC2, legacy PEM encryption headers and unsupported PBES2 algorithms remain unsupported. JDK 21 SunJCE evidence (`Cipher.getInstance`) recognizes `PBEWithMD5AndDES`, `PBEWithSHA1AndDESede`, and `PBEWithSHA1AndRC2_40`, but reports `NoSuchAlgorithmException` for `PBEWithSHA1AndDES`, `PBEWithMD2AndDES`, and `PBEWithMD5AndRC2`; Java provider selection is external and Java `TlsHelper` delegates decryption/key parsing to Netty/JCA rather than defining a RocketMQ key format. Thus the remaining PBES1 algorithm gaps are not claimed equivalent; SHA1/DES is unavailable in the tested JDK provider, while MD2/RC2 support is provider-dependent. The Java fixture's 512-bit RSA key is decrypted/parsed but cannot be loaded by the selected rustls provider; the matching 2048-bit Java PBES2 fixture verifies provider loading. This is parsing/decryption parity; key algorithms and minimum sizes are additionally constrained by the selected rustls crypto provider.
- Transport lifecycle remains intentionally non-equivalent where Java depends on Netty thread/event-loop identity. Earlier Phase 3 dispositions accepted Tokio worker identity, polling, scheduling, shutdown/drain, and executor lifecycle differences; under the current parity contract these remain acceptable only where public capabilities/settings and observable operation behavior still correspond to Java 5.5.1. The earlier inventory also treated the lower-level `RemotingClient` transport configuration snapshot as accepted against Java's mutable `NettyClientConfig`. The Phase 3 inventory now records each Remoting setting's Java read/capture boundary and its Rust adapter or snapshot behavior, including live updates and construction/start/proxy-CIDR/per-channel snapshots; this closes that timing-inventory slice; the broad P18-V01 audit later closed at 0cf294b710d06d40bd72ccec1ca5d1df121c5225, and its current-tree delta is recorded in the MAN-05 audit. Core `ClientRuntime::config()` exposes a shared mutable `ClientConfig` like `MQClientInstance.getClientConfig()` (ADR-0037). Earlier Phase 3 rows also classified queued-byte writability/watermark accounting versus Netty outbound-buffer accounting, NameServer scan deferral versus Java executor rejection and related scheduling/list/wrapper behavior, and historical API gaps around Netty/JVM carriers (`Channel`, `ChannelHandlerContext`, `ResponseFuture`, `ChannelWrapper`). Rust now maps callback/future channel capabilities with `ResponseFuture` and identity-preserving `ChannelHandle` values. Inbound processors and request-pipeline stages receive a shared Rust `RequestContext` with channel identity, peer address, close, and no-deadline write enqueue; raw Netty objects, the rest of the handler-context surface, wrapper internals, and Tokio sockets remain framework-specific. The pinned `NettyRequestProcessor` review closes the `ChannelHandlerContext` RocketMQ-capability question: Java declares `processRequest(ctx, request)` and default `rejectRequest()`, and Rust maps them to `RequestProcessor::process_with_request_context` and `reject_request`. RocketMQ request handling uses one identity-preserving `RequestContext` with peer address, channel state, close, and typed-command writes. Allocator, handler propagation, arbitrary-object writes, promises, and raw Netty channel APIs remain framework-specific; Tokio does not emulate that Netty surface. The processor, pipeline, and hook response categories, opaque values, one-way suppression, aborts, and callback order are now checked against pinned Java `NettyRemotingAbstract.processRequestCommand` by the invoked `inboundFailureFlows` fixture and Rust test `p18_inbound_hook_pipeline_and_processor_failures_match_java_flow_fixture`. Exact Java exception remarks still include exception and stack-frame rendering that Rust does not reproduce; this remains a diagnostic difference, not an unresolved response-flow mismatch. Rust construction validates configuration and retains worker receivers; callers must invoke `RemotingClient::start()` inside an active Tokio runtime before transport operations. `start()` is idempotent; invoke APIs return `NotStarted` and address reachability is false before start. Shutdown before start discards retained receivers and prevents a later start. Java channel-event queue admission is bounded to 10001 in both; polling and scheduling remain different, while shutdown now maps Java's up-to-90-second synchronous event-worker join boundary. Tokio idle timer expiry emits/closes from the connection task and does not reproduce Netty timer scheduling precision. Channel-event callbacks receive an identity-preserving Rust-owned `ChannelHandle` with peer address, state, close, and write operations; connection generation remains private transport bookkeeping. This maps the public Java channel capability without fabricating a Netty `Channel` or exposing a raw Tokio socket. Fatal Rust transport/protocol failures now queue EXCEPTION then CLOSE, matching Java's exceptionCaught-triggered close lifecycle; ordinary EOF/close queues CLOSE. Java `NettyRemotingClient.shutdown()` closes channels and requests graceful event-loop shutdown, then calls `NettyEventExecutor.shutdown()`; inherited `ServiceThread.shutdown()` joins that event thread for up to 90 seconds. It subsequently calls `ExecutorService.shutdown()` for the public and scan executors without waiting for their work to finish. Rust `shutdown().await` now keeps public-executor admission open through the same join or deadline boundary, then closes admission without waiting for accepted work; transport cleanup and accepted callbacks continue in a background task. The callback queue is signaled after transport work and the channel-event worker finish or reach the deadline, preserving queued completions. A blocking callback cannot be forcibly stopped and may continue after `shutdown()` returns. Tokio polling and cleanup scheduling remain implementation-specific.
